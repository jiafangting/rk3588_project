# rk3588 主进程开发日志

## 1. 开发目标

这个 `rk3588` 目录是离线工业巡检系统的 C 语言主进程层，目标是把已经完成的 Python 视觉模块和语音模块统一调度起来，形成一个可以在 RK3588 Linux 上长期运行的巡检主控程序。

当前主进程的核心目标是：

- 启动和管理多线程；
- 读取 STM32 传感器数据；
- 查询 Python 视觉模块状态；
- 融合传感器和视觉结果做决策；
- 触发报警执行动作；
- 监控线程心跳；
- 加载阈值配置；
- 支持无硬件情况下的模拟运行；
- 后续可继续接入消息队列、串口和外设联动。

---

## 2. 当前已经完成的工作

### 2.1 主入口和线程框架

已经完成了主进程入口 `main.c`，并且启动了 5 个核心线程：

- `thread_sensor`：串口接收 STM32 传感器数据；
- `thread_vision`：定时查询视觉模块状态；
- `thread_decision`：融合判断，触发报警；
- `thread_alarm`：执行报警动作；
- `thread_heartbeat`：心跳监控。

主线程负责：

- 初始化全局状态；
- 加载配置文件；
- 注册退出信号；
- 等待所有线程正常退出；
- 收尾释放资源。

### 2.2 全局状态结构体

已经定义了统一的 `SystemState`，把所有线程需要共享的数据集中在一起，包括：

- 传感器数据：温度、湿度、设备温度、电流、烟雾；
- 视觉数据：状态、人头数量、禁区命中、报警类型；
- 系统状态：当前报警是否激活、最后一次报警原因、报警时间、当天报警次数；
- 线程心跳时间戳。

### 2.3 阈值配置模块

已经完成 `threshold_config.c/.h`，支持：

- 从 `config.json` 加载阈值；
- 不依赖第三方 JSON 库；
- 文件缺失时自动使用默认值；
- 保证没有配置文件也能启动。

### 2.4 传感器线程基础框架

已经完成 `thread_sensor.c` 的基础逻辑：

- 串口优先读取 `/dev/ttyS3`；
- 串口打开失败时自动切换模拟模式；
- 模拟模式会每秒生成一组传感器数据；
- 每次更新后刷新心跳。

### 2.5 视觉线程基础框架

已经完成 `thread_vision.c` 的基础逻辑：

- 每 2 秒通过 Unix Domain Socket 查询视觉模块；
- 解析视觉模块返回的 JSON；
- 更新视觉状态、人头数量、禁区命中和报警类型；
- 连接失败时不崩溃，只打印警告并重试。

### 2.6 决策线程基础框架

已经完成 `thread_decision.c` 的融合判断框架：

- 结合传感器和视觉判断报警；
- 支持温度、湿度、电流、设备温度、烟雾报警；
- 支持视觉 `ALARM` 和禁区命中报警；
- 具备报警冷却思路；
- 预留了消息队列接口位置。

### 2.7 报警线程基础框架

已经完成 `thread_alarm.c` 的基础报警执行逻辑：

- 报警激活时打印报警日志；
- 追加写入 `alarm_log.csv`；
- 预留串口给 STM32 发送蜂鸣器/LED 指令；
- 报警解除时关闭硬件报警。

### 2.8 心跳监控线程

已经完成 `thread_heartbeat.c`：

- 每 10 秒检查一次各线程心跳；
- 超过 30 秒未更新时打印警告；
- 只监控，不自动重启。

### 2.9 项目基础文件

已经补齐：

- `config.json`；
- `alarm_log.csv`；
- `Makefile`；
- `README.md`。

## 3. 主要问题记录

### 问题 1：没有统一的主进程入口
- 现象：Python 视觉和语音模块虽然都完成了，但没有一个统一的 C 主程序负责调度。
- 原因：系统处于分模块开发阶段，缺少主控层。
- 处理：新增 `main.c`，统一启动和管理各线程。

### 问题 2：没有统一的系统状态共享结构
- 现象：传感器、视觉、报警、心跳数据分散，线程之间不好协作。
- 原因：缺少集中共享的数据结构。
- 处理：定义 `SystemState`，把所有核心状态放到一起，由互斥锁保护。

### 问题 3：没有配置文件时系统不好调
- 现象：阈值写死后，现场调试会很麻烦。
- 原因：阈值没有从文件读取。
- 处理：新增 `config.json` 和 `threshold_config.c`，支持默认值回退。

### 问题 4：硬件未到货时程序无法验证
- 现象：没有 STM32 或传感器串口时，主程序无法继续跑。
- 原因：所有逻辑都依赖真实硬件。
- 处理：传感器线程增加模拟模式，串口不可用时自动生成模拟数据。

### 问题 5：视觉模块和 C 主进程还没真正联动
- 现象：Python 视觉模块虽然已经能输出状态，但 C 端还没有统一查询和消费它。
- 原因：缺少视觉 socket 调用线程。
- 处理：新增 `thread_vision.c`，通过 Unix Socket 定时查询视觉状态。

### 问题 6：报警动作和报警判断还没真正收口
- 现象：报警触发、报警关闭、报警日志、硬件指令分散在不同逻辑里。
- 原因：报警链路还未完全统一。
- 处理：新增决策线程和报警线程，把报警触发与执行分开处理。

### 问题 7：线程存活状态看不出来
- 现象：程序运行时，某个线程卡住后不容易发现。
- 原因：缺少统一的健康检查。
- 处理：新增心跳数组和心跳监控线程。

### 问题 8：消息队列还没真正接通
- 现象：决策线程和报警线程之间还没有真正通过 `/mq_alarm` 通信。
- 原因：当前优先先搭骨架和主循环，消息队列接口还在预留阶段。
- 处理：先定义报警消息结构，并在代码里预留消息队列位置，后续再接 `mq_open / mq_send / mq_receive`。

## 4. 当前成果总结

截至目前，`rk3588` C 主进程已经从“没有统一控制层”进展到“有完整主控框架”的阶段：

- 已经有主入口 `main.c`；
- 已经有统一系统状态 `SystemState`；
- 已经有 5 个线程骨架；
- 已经有阈值配置文件和默认值回退；
- 已经支持串口失败时切换模拟数据；
- 已经可以查询视觉模块状态；
- 已经可以进行传感器 + 视觉融合判断；
- 已经可以记录报警日志；
- 已经可以监控线程心跳；
- 已经具备后续接入消息队列和硬件外设的基础。

也就是说，主控层已经不再只是一个空壳，而是已经搭好了后续真正联调的基础框架。
