# vision 开发日志

## 1. 开发目标

这个 `vision` 模块是整个视觉巡检系统的正式业务层，目标不是做一个“能跑”的 demo，而是做一个“能长期稳定运行”的巡检程序。

当前视觉巡检程序的核心目标是：
- 打开摄像头并稳定显示画面
- 使用 YOLO 进行目标检测
- 识别人员、火焰、烟雾等目标
- 判断是否进入禁区
- 识别结果稳定后再触发语音播报和报警联动
- 保存图片、日志和可选的视频片段
- 保证正式入口稳定清晰，不被测试代码干扰

## 2. 目录职责划分

### `vision/app/config.py`
统一管理参数配置。

### `vision/app/vision_core.py`
视觉核心能力，负责检测、判断、播报、画图、报警判断。

### `vision/app/vision_logger.py`
日志保存，负责 JSONL、CSV、记录结构、截图和视频片段保存。

### `vision/app/vision_bridge.py`
视觉联动桥，负责报警落盘、记录缓存、查询支持、串口联动、最近报警截图管理。

### `vision/app/vision_pipeline.py`
主流程调度，负责串起视觉、语音、日志、保存、退出。

### `vision/app/vision_main.py`
正式入口，只负责启动主流程。

### `vision/app/run_notes.py`
正式版运行说明。

### `run_vision.py`
根目录统一入口，只负责启动正式业务流程。

## 4. 主要问题记录

### 问题 1：Python 环境里没装 OpenCV
- 现象：执行 `import cv2` 时提示没有 `cv2`
- 原因：当前终端用的 Python 不是 `rk3588-ai` 环境里的 Python
- 处理：切换到 `rk3588-ai` 环境后再检查，确认 OpenCV 已安装

### 问题 2：摄像头画面读取失败
- 现象：摄像头能打开，但读取帧失败
- 原因：Windows 默认摄像头后端不稳定，MSMF 抓帧容易出问题
- 处理：打开摄像头时优先使用 `CAP_DSHOW`，再回退默认方式

### 问题 3：终端路径不对，脚本找不到
- 现象：运行脚本时提示找不到 `vision_camera_test.py`
- 原因：当前目录没有切到 `E:\rk3588_project`
- 处理：先切盘再进入项目目录，再运行脚本

### 问题 4：预览窗口不容易退出
- 现象：窗口开了以后，按键有时不生效
- 原因：预览窗口没有获得焦点，或者 Python 进程还在运行
- 处理：点到窗口里按 `q`，不行就直接在终端里 `Ctrl + C`

### 问题 5：画面上中文显示乱码
- 现象：把中文结果写到 OpenCV 画面上后出现乱码
- 原因：OpenCV 的 `cv2.putText()` 对中文支持不好，直接写中文容易变成方块或乱码
- 处理：先把画面上的说明文字改成英文显示，后面如果要显示中文，再考虑用其他字体方案

### 问题 6：单帧判断太敏感，结果会抖动
- 现象：摄像头轻微移动后，YOLO 检测结果会一会儿正常、一会儿异常，甚至人数判断来回跳
- 原因：通用 YOLO 模型对运动模糊、视角变化、光照变化比较敏感，而且当前只是单帧判断
- 处理：改成连续 5 帧稳定人数多数投票后再确认状态，最近 5 帧里至少 3 帧一致才算稳定，不再看单帧结果；并把 1 个 person 视为正常、0 人和 2 人及以上都视为异常

### 问题 7：单人被误判成两人
- 现象：画面里明明只有 1 个人，模型有时会识别成 2 个，导致状态在 NORMAL 和 ABNORMAL 之间来回切换
- 原因：通用 YOLO 模型对当前场景不够专用，且单帧结果仍然会有抖动和误检
- 处理：把人员判定从“看当前这一帧”改成“看最近几帧的多数结果”，并继续通过提高置信度阈值、连续帧确认、固定机位或换巡检专用模型来优化

### 问题 8：巡检记录还没真正落盘成统一文件
- 现象：前面的流程已经能识别、判断和保存图片，但巡检结果还主要停留在终端打印阶段
- 原因：还没有把每次巡检结果统一整理并保存成标准记录文件
- 处理：新增 `vision_inspection_record_test.py`，把结果保存到 JSONL / CSV，同时记录图片路径，方便后面追踪和归档

### 问题 9：视觉结果还没有和语音真正联动
- 现象：视觉侧已经能稳定判断状态，但还只是打印结果，没有主动播报
- 原因：还没有把视觉结果映射到语音播报内容
- 处理：新增 `vision_voice_broadcast_test.py`，将视觉状态转成播报文本并通过本地 TTS 播报出来

### 问题 10：语音脚本第一次能播，后面状态变化却没有声音
- 现象：第一次状态稳定后，终端里能看到 `TTS:` 和第一次播报，但后面即使状态又稳定变化，终端有时也没有新的声音
- 原因：`pyttsx3` 在 Windows 上复用同一个引擎时，可能出现引擎状态卡住、后续播报失效或者队列不再正常执行的情况；另外，状态本身在摄像头画面里也会来回跳，如果没真正连续稳定到 3 帧，就不会触发播报
- 处理：把语音播报改成更稳的后台线程队列方式，每次播报都通过队列交给单独线程执行，并保留“连续 3 帧状态一致后才播报”的规则，避免重复播报和引擎复用失效

### 问题 11：语音播报时画面会卡住
- 现象：一旦触发语音播报，摄像头画面会短暂停住，等播报结束后才继续刷新，看起来像“播报把画面挡住了”
- 原因：之前的写法是终端先打印，再在主循环里直接调用 `engine.runAndWait()`，播完才继续下一帧，这会一直阻塞当前线程；而主循环还要负责读摄像头、YOLO 推理和画面刷新，所以语音一播报，整个画面就会被卡住
- 处理：把播报改成后台异步线程方式。现在主线程只负责读摄像头、跑 YOLO 和刷新画面；语音线程专门从队列里取播报文本并播放，这样播报和画面刷新互不阻塞，画面就不会再一播报就卡住

### 问题 12：报警状态会正常和报警来回跳
- 现象：禁区里有人或者报警目标还在时，画面状态会一会儿正常、一会儿报警，看起来像循环跳动
- 原因：报警没有真正锁定，普通稳定判断和报警判断在不同帧里互相覆盖，导致刚报警又被普通状态写回去
- 处理：增加报警锁定机制，报警触发后保持 `ALARM`，只有连续几帧都没有报警信号才解除锁定，避免正常/报警来回跳

### 问题 13：主入口偶尔被覆盖后导入失败
- 现象：运行 `run_vision.py` 时提示 `cannot import name 'main' from 'vision_pipeline'`
- 原因：在频繁调整视觉主流程时，`vision_pipeline.py` 里的 `main()` 入口曾被覆盖丢失，导致 `vision_main.py` 无法导入主函数
- 处理：收口入口结构，固定 `run_vision.py -> vision_main.py -> vision_pipeline.py` 这条链路；以后主要只改主流程内部，不随意覆盖入口函数

### 问题 14：报警和正常状态显示互相覆盖
- 现象：报警中偶尔会出现正常状态文字，或者刚退出报警又立刻回到正常播报
- 原因：普通状态播报逻辑和报警锁定逻辑没有彻底隔离，导致状态文字在不同帧里互相覆盖
- 处理：把报警锁定逻辑优先级提到最高，报警期间禁止普通状态播报和覆盖，只有报警信号消失一段时间后才允许恢复普通状态

### 问题 15：无人状态误判太频繁
- 现象：画面里明明一直有人，但程序总提示“没人”或者 `ABNORMAL`
- 原因：单帧漏检和置信度波动导致当前帧的 person 数量经常掉到 0
- 处理：把人员稳定确认改成最近几帧多数结果判断，并且无人状态也要连续几帧稳定后才确认，避免一帧漏检就直接判无人

### 问题 16：稳定历史被重复写入
- 现象：稳定窗口里的人数变化太快，判断结果会偏乱
- 原因：`process_one_frame()` 里和 `build_decision()` 里同时对 `stable_person_history` 做了写入，导致每帧被记录两次
- 处理：删掉 `process_one_frame()` 里的手动写入，只保留 `build_decision()` 里统一写入

### 问题 17：画面和报警联动还不够直观
- 现象：虽然已经有报警和禁区，但画面上状态不够醒目，人数提示也不够直观
- 原因：结果图信息显示得不够集中
- 处理：增加状态面板、报警横幅、当前帧人数提示、禁区加粗显示，让画面一眼就能看出当前状态

### 问题 18：报警联动还没有统一收口到一个桥模块
- 现象：视觉报警、保存截图、记录缓存、语音查询、STM32 串口联动这几块功能还需要一个统一中间层
- 原因：之前的代码主要集中在主流程里，模块间联动还不够清晰
- 处理：新增 `vision_bridge.py`，统一管理报警落盘、记录缓存、查询支持、串口联动、最近报警截图

### 问题 19：语音触发巡检保存只收到 ACK，没有真正返回保存结果
- 现象：语音侧说“帮我保存一下”时，会向视觉 socket 发送 `trigger_inspection`，但视觉 socket 只返回 ACK。语音客户端等待包含 `status` 的视觉结果，容易卡到超时；同时视觉主流程没有真正调用当前帧保存逻辑，导致“已保存当前巡检记录”可能只是口头确认。
- 原因：`VisionSocketServer` 的 `trigger_inspection` 没有把命令交给 `vision_pipeline.py` 的当前帧上下文处理；`vision_pipeline.py` 启动 socket 服务时也没有传 `command_callback`。socket 层和主流程之间缺少“命令 -> 当前帧截图 -> 写入 JSONL/CSV -> 返回路径”的闭环。
- 处理：让 socket 命令回调可以返回完整 JSON；在 `vision_pipeline.py` 中保存最近一帧的 `preview / result_image / decision / live_frame_path` 上下文；收到 `trigger_inspection` 后调用 `bridge.manual_snapshot()` 真正落盘，并返回 `status / person_count / reason / raw_path / result_path / snapshot_path`。如果画面尚未准备好，则返回 `status=UNKNOWN` 的错误结果，避免语音侧一直等待超时。
- 当前结果：语音触发“帮我保存一下”后，视觉侧会保存当前巡检截图和记录，并把保存路径返回给语音模块播报。
