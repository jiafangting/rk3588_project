# voice 开发日志

## 1. 开发目标

`voice` 目录是整个项目里的语音交互模块，目标不是只做“能听”和“能说”，而是做一个可以和视觉模块联动的完整语音控制系统。

当前语音模块的核心目标是：

- 麦克风监听；
- 自动静音结束；
- 保存录音为 `test.wav`；
- 中文语音识别；
- 唤醒词触发；
- 待机模式 / 工作模式切换；
- 根据指令播报回复；
- 长时间无有效语音自动回待机；
- “停止 / 退出 / 结束”退出程序；
- 能查询视觉报警记录；
- 能触发视觉模块保存巡检截图；
- 后续可继续接 STM32 串口联动。

## 2. 当前已经完成的工作

### 2.1 录音与语音识别

已经完成了基础的语音输入链路：

- 麦克风能采集声音；
- 识别静音后自动结束录音；
- 录音会保存成 `test.wav`；
- 语音识别可以识别中文；
- 能把识别结果转成文字命令。

### 2.2 唤醒词与模式切换

已经实现了唤醒词触发机制：

- 识别到唤醒词后进入工作模式；
- 没有有效输入时保持待机；
- 长时间没有有效语音后自动回到待机；
- 可以通过“停止 / 退出 / 结束”退出程序。

### 2.3 语音指令回复

已经实现了基本的语音播报回复：

- 问当前温度、当前模式等问题时，会播报对应回答；
- 可以根据识别到的指令进行 TTS 回复；
- 能把语音识别结果转成可播报文本。

### 2.4 视觉联动预留

已经考虑了与视觉模块联动：

- 可以触发视觉模块保存巡检结果；
- 可以读取视觉模块状态；
- 可以把视觉报警结果反馈给语音播报。

### 2.5 测试脚本已经分离

目前语音模块相关脚本已经拆开，便于单独测试：

- `voice_loop.py`：语音主循环；

## 3. 主要问题记录

### 问题 1：录音太短或太长
- 现象：录音有时太短，识别不完整；有时又太长，等很久才结束。
- 原因：静音检测阈值和静音时长设置不合适。
- 处理：通过调节静音阈值和连续静音帧数来优化录音结束时机。

### 问题 2：中文语音识别结果不稳定
- 现象：同一句话有时识别正确，有时识别成别的内容。
- 原因：环境噪声、麦克风质量、识别模型和说话方式都会影响结果。
- 处理：优先使用固定表达的唤醒词和固定命令词，减少自由口语导致的不稳定。

### 问题 3：唤醒词误触发
- 现象：有时环境里一些类似发音会误触发工作模式。
- 原因：唤醒词设置过于接近日常语音，或者识别阈值太低。
- 处理：收紧唤醒词识别策略，并尽量使用固定词组。

### 问题 4：TTS 播报卡顿
- 现象：播报时程序会卡一下，或者播报与下一轮识别互相影响。
- 原因：语音播报和主识别流程没有完全分离。
- 处理：把播报放到独立逻辑里，尽量避免阻塞主循环。

### 问题 5：命令解析不统一
- 现象：同一个意思的说法很多，程序不一定都能理解。
- 原因：命令词没有统一整理，解析逻辑还比较初级。
- 处理：优先支持少量固定命令词，再逐步扩充同义表达。

### 问题 6：视觉联动还没完全收口
- 现象：语音模块想查询视觉记录时，视觉侧接口还需要继续整理。
- 原因：视觉模块和语音模块之间的通信链路还在完善。
- 处理：先保留查询接口和控制接口，再逐步收紧为统一桥接模块。

### 问题 7：终端编码或中文输入问题
- 现象：在 Windows 终端里输入中文时，有时会因为编码或管道问题出错。
- 原因：不同终端环境的编码支持不完全一致。
- 处理：保留英文调试词作为备选输入，同时使用固定命令词更稳。

### 问题 8：报警记录查询和手动保存接口还没完全接通
- 现象：用户希望通过语音问“有没有报警记录”“最近一次报警是什么”“帮我保存一下”，但早期代码只做了基础唤醒和模式切换。
- 原因：语音命令没有对接视觉模块的 JSONL / CSV 报警记录，也没有把“手动保存”与视觉巡检保存动作真正打通。
- 处理：在 `voice_loop.py` 里新增报警记录查询、手动保存触发和语音确认回复逻辑，后续再继续和视觉模块状态对齐。

### 问题 9：视觉已经报警，但语音询问“有没有报警”仍回答没有记录
- 现象：视觉画面已经进入报警状态，用户问语音“有没有报警”时，语音模块仍可能回答“今天还没有报警记录”。
- 原因一：视觉侧报警日志写入的是 `alarm_type / alarm_time / alarm_reason` 结构，例如 `alarm_type=right_third_zone`，不一定带有 `status=ALARM`。旧版语音查询只认 `status == ALARM` 或 `alarm_type` 里包含英文 `alarm`，所以会漏掉真实禁区报警。
- 原因二：语音侧只读本地 JSONL / CSV 历史文件，没有优先查询视觉模块实时 socket 状态。视觉刚报警但还没完成写文件时，语音就拿不到当前报警。
- 解决方法一：在 `voice_loop.py` 中新增 `is_alarm_record()`，把包含 `alarm_type`、`alarm_time`、`alarm_reason` 或 `zone_name` 的记录都视作报警记录，兼容旧版和新版视觉日志格式。
- 解决方法二：在 `reply_alarm_query()` 中优先调用 `VisionSocketClient.get_status()` 查询视觉实时状态；如果当前状态是 `ALARM`，直接播报“现在有报警”，再用文件记录作为兜底。
- 解决方法三：在 `vision_pipeline.py` 中启动 `VisionSocketServer`，并在每帧处理后发布当前 `status / person_count / reason / zone_name / intruded_people / alarm_frame_count`，让语音模块可以实时查询视觉状态。
- 播报优化：视觉内部的英文调试原因，例如 `Intrusion into hazard zone`，在语音侧通过 `format_alarm_reason()` 转成中文“检测到人员进入禁区”，避免 TTS 念英文调试文本。
- 当前结果：语音问“有没有报警”时，优先返回实时视觉报警；视觉未运行时，自动读取历史报警记录；两条路径都失败时才回答没有报警记录。

## 4. 当前成果总结

截至目前，`voice` 语音模块已经从“单纯录音测试”进展到“可以和视觉模块联动的语音控制模块”的阶段：

- 能监听麦克风；
- 能识别中文语音；
- 能自动结束录音；
- 能保存录音文件；
- 能唤醒并切换到工作模式；
- 能根据命令播报回复；
- 能停止退出；
- 已经预留了视觉联动入口；
- 已经预留了报警记录查询能力；
- 已经支持“帮我保存一下”这类手动触发保存；
- 已经具备继续扩展成“语音查询视觉记录”的基础。

也就是说，语音模块现在已经不是单独的语音测试脚本，而是一个可以参与整个巡检系统联动的正式模块。

## 5. 当前开发方向

现在语音模块的开发方向已经从“让它能听、能说”转向“让它和视觉系统真正连起来”：

- 保持唤醒词稳定；
- 保持待机 / 工作模式清晰；
- 保持命令词简单明确；
- 保持 TTS 播报稳定；
- 保持与视觉模块的接口清楚；
- 保持后续和 STM32 的串口扩展空间。

后面如果继续改，优先方向会是：

1. 语音查询视觉报警记录；
2. 语音触发手动保存巡检截图；
3. 更自然的播报回复；
4. 与视觉报警状态联动播报；
5. 后续接入串口设备控制蜂鸣器或 LED。

## 7. 未来整理建议

如果后面继续优化，建议按下面顺序来：

1. 先把语音指令词统一；
2. 再把视觉查询接口固定；
3. 再把报警记录查询做完整；
4. 最后再扩展串口设备联动。

## 8. 结论

目前 `voice` 模块已经具备完整的语音交互基础，并且开始向“语音控制视觉巡检系统”的方向收口。

这几块整理成一条稳定、清楚、好维护的链路。
